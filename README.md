# 🦊 Foxora2 — ربات مدیریت گروه و ضد اسپم سروش پلاس (نسخهٔ دوم کاملاً مستقل)

**Foxora2** یک کپی کامل و کاملاً مستقل از ربات Foxora برای سروش پلاس است. تمام قابلیت‌ها، دستورات، بازی‌ها، اقتصاد، مدیریت گروه، قالب‌بندی پیام‌ها (Bold / Quote / Spoiler) و فهرست‌های داده بدون هیچ تغییری حفظ شده‌اند، اما **مسیر نصب، مسیر داده‌ها، دیتابیس، لاگ‌ها، فایل قفل پروسه (PID / Watchdog) و نشست (Session)** کاملاً از ربات `Foxora` و ربات `B2` جدا هستند.

---

## 🔒 جداسازی کامل از ربات‌های دیگر (`Foxora` و `B2`)

| مورد | ربات `Foxora2` (این مخزن) | ربات `Foxora` (اصلی) | ربات `B2` |
|---|---|---|---|
| پوشهٔ کد پروژه | `~/Foxora2` | `~/Foxora` | پوشهٔ جداگانهٔ B2 |
| شناسهٔ نمونه (`.bot_instance` / `BOT_INSTANCE`) | `foxora2` | `foxora` | `main` |
| مسیر داده‌ها، دیتابیس و لاگ | `~/.foxora2/` | `~/.foxora/` | `~/.local/share/soroush-bot/` |
| دیتابیس SQLite | `~/.foxora2/db/bot.sqlite3` | `~/.foxora2` ندارد (`~/.foxora/db/bot.sqlite3`) | `~/.local/share/soroush-bot/db/bot.sqlite3` |
| فایل قفل پروسه و واچ‌داگ | `~/.foxora2/config/bot.pid` و `watchdog.lock` | `~/.foxora/config/bot.pid` و `watchdog.lock` | مسیر مستقل B2 |
| متغیر نشست در `.env` | `SOROUSH_SESSION_STRING_FOXORA2` | `SOROUSH_SESSION_STRING_FOXORA` | `SOROUSH_SESSION_STRING` |
| دستور اجرا / توقف | `./foxora2` و `python3 foxora2.py` | `./foxora` و `python3 foxora.py` | مستقل |

> ⚠️ **مهم:** یک حساب سروش (یک `SOROUSH_SESSION_STRING`) نمی‌تواند همزمان روی دو پروسهٔ فعال اجرا شود؛ سرور MTProto آپدیت‌ها را فقط به یکی می‌دهد. برای اجرای همزمان `Foxora2` در کنار `Foxora` و `B2`، حتماً یک حساب سروش جداگانه برای `Foxora2` بسازید و نشست آن را در `SOROUSH_SESSION_STRING_FOXORA2` بگذارید.

## 📦 نصب و راه‌اندازی در Termux یا لینوکس

### ۱. کلون کردن در پوشهٔ مستقل
```bash
git clone https://github.com/splusesupor-oss/Foxora2.git ~/Foxora2
cd ~/Foxora2
```

### ۲. نصب پیش‌نیازها
```bash
pip install -r requirements.txt
```

### ۳. ساخت فایل `.env` و تنظیم نشست اختصاصی `Foxora2` (بدون نیاز به API ID / API Hash)
```bash
cp .env.example .env
python3 tools/login_primary_once.py
```
کتابخانهٔ `SPlusthon` به‌طور پیش‌فرض مقادیر رسمی کلاینت سروش‌پلاس را درون `SoroushClient(StringSession())` دارد؛ بنابراین **هیچ نیازی به وارد کردن دستی `API_ID` و `API_HASH` نیست**. ابزار `tools/login_primary_once.py` فقط شماره تلفن، کد تأیید و (در صورت فعال بودن) رمز دومرحله‌ای حساب سروش‌پلاس را می‌پرسد و رشتهٔ نشست را مستقیماً و فقط در متغیر اختصاصی `SOROUSH_SESSION_STRING_FOXORA2` داخل `~/Foxora2/.env` ذخیره می‌کند (بدون دست‌زدن به نشست یا فایل‌های `Foxora` و `B2`).

همچنین می‌توانید فایل `.env` را دستی ویرایش کنید (`nano .env`):
```env
BOT_INSTANCE=foxora2
SOROUSH_SESSION_STRING_FOXORA2=رشته_نشست_حساب_جدید_سروش
```

## ▶️ اجرای ربات `Foxora2`

| دستور | عملکرد |
|---|---|
| `./foxora2` | اجرای ربات با واچ‌داگ اختصاصی (پیشنهادی برای اجرای دائمی) |
| `./foxora2 direct` یا `python3 foxora2.py` | اجرای مستقیم بدون واچ‌داگ |
| `./foxora2 status` | نمایش وضعیت فعلی، PID و مسیر داده‌های `Foxora2` |
| `./foxora2 stop` | توقف **فقط** ربات `Foxora2` (ربات‌های `Foxora` و `B2` دست‌نخورده می‌مانند) |

اگر `./foxora2` خطای دسترسی داد، یک‌بار دستور زیر را بزنید:
```bash
chmod +x foxora2 foxora2.py
```

## 🗂️ مسیر ذخیرهٔ اطلاعات `Foxora2`

تمام فایل‌های زمان اجرا به صورت خودکار در `~/.foxora2` ساخته می‌شوند:
- `~/.foxora2/config/` — گروه‌های فعال (`groups.json`)، ادمین‌ها (`admins.json`)، قوانین، کلمات، اقتصاد، کلیپ‌بورد، قفل پروسه (`bot.pid` و `watchdog.lock`) و تنظیمات
- `~/.foxora2/db/bot.sqlite3` — دیتابیس SQLite اختصاصی `Foxora2`
- `~/.foxora2/logs/` — لاگ‌های زمان اجرا (`bot_runtime.log`، `watchdog.log`)، پیام‌های حذف‌شده و آمار گروه‌ها
- `~/.foxora2/backups/` و `~/.foxora2/archive/` — پشتیبان‌ها و آرشیوها
- `~/.foxora2/court_game/` — دادهٔ دائمی بازی «دادگاه روباه» (`cases/`، `sessions/`، `ai_logs/`، `results/`، `config/`)

در صورت نیاز به تغییر مسیر داده‌ها می‌توانید متغیر زیر را در `.env` قرار دهید:
```env
SOROUSH_BOT_DATA_DIR_FOXORA2=/custom/path/for/foxora2
```

## 🔒 عضویت اجباری کانال (Force Join)

هر گروه می‌تواند یک کانال اجباری داشته باشد: تا کاربر عضو آن کانال نشود،
پیامش در گروه حذف می‌شود. قابلیت عمداً «کم‌مصرف» طراحی شده است — مسیر هر
پیام **صفر فراخوانی API** دارد (کش حافظه → SQLite → حداکثر یک بررسی وقتی
وضعیت کهنه است).

> ⚠️ **واقعیت مهم سرور سروش:** `channels.getParticipant` روی سروش پیاده
> نشده است (`422 NOT_SUPPORTED`). پس بررسی عضویت **چندمسیره** است و اولین
> مسیری که جواب بدهد استفاده می‌شود:
> `getParticipant` → **Bot API `getChatMember`** (روش ربات‌های تلگرامی) →
> جست‌وجوی هدفمند عضو → **پیمایش هدفمند اعضا** (حکم قطعی برای همان کاربر) →
> اسنپ‌شات کامل اعضا. اگر هیچ مسیری جواب نداد،
> عضویت اجباری فعال **نمی‌شود** (پیام کسی بی‌دلیل حذف نمی‌شود).

- دستورها (فقط مالک گروه/مالک ربات؛ «وضعیت کانال» برای همه):
  `کانال من <لینک یا آیدی>` ، `حذف کانال من` ، `وضعیت کانال` ،
  `تنظیم عضویت اجباری` ، `لغو عضویت اجباری` ،
  `تست عضویت` (با ریپلای: «عضو هست» یا «عضو نیست»)،
  `تشخیص عضویت` (گزارش کامل فنی)، `راهنمای کانال`، `راهنمای اجرا`
- هنگام ثبت، ربات واقعاً **هر مسیر** را یک‌بار می‌سنجد
  (`getParticipant`، `getChatMember`، خواندنی بودن فهرست اعضا، ادمین بودن از
  فهرست ادمین‌ها، `can_view_participants` / `participants_hidden`) و نتیجه
  را ذخیره می‌کند تا مسیر مرده دوباره صدا زده نشود. اگر هیچ مسیری نباشد،
  قابلیت **فعال نمی‌شود** و دلیلش به مالک گفته می‌شود.
- در قطعی/تایم‌اوت API هیچ پیامی حذف نمی‌شود (fail-open) و «عضو نیست» از
  «دسترسی نداریم» تفکیک می‌شود.
- خروج از کانال با رویداد `UpdateChannelParticipant` فوراً باطل می‌شود؛
  اسنپ‌شات دوره‌ای + diff محلی، خروج‌های بی‌رویداد را می‌گیرد (اسنپ‌شات
  ناقص هرگز کسی را «خارج‌شده» ثبت نمی‌کند).
- **به‌محض ورود کاربر به گروه**، اگر عضویت کانال تأیید نشود همان لحظه لینک
  کانال برایش ارسال می‌شود (`FORCE_JOIN_NOTICE_ON_JOIN`)، و به‌محض اینکه
  عضو کانال شد پیام «✅ عضویت شما تأیید شد» می‌آید — حتی اگر حساب ربات
  ادمین کانال نباشد (صف تأیید، بدون نیاز به رویداد سرور).
- معاف: مالک ربات، مالک گروه، ادمین ثبت‌شده، ادمین واقعی گروه، VIP، ربات‌ها
  و پست‌های کانالی.

مستندات کامل (گزارش فنی سورس‌محور، معماری، اعداد بنچمارک و محدودیت‌های
صادقانه): [`docs/FORCE_JOIN.md`](docs/FORCE_JOIN.md)

```bash
python3 -m pytest tests/test_force_join.py -q    # ۸۳ تست
python3 tools/bench_force_join.py --messages 1000

# سنجش زنده: با این حساب کدام روش بررسی عضویت روی سروش جواب می‌دهد؟
# (ربات باید خاموش باشد؛ ابزار فقط می‌خواند)
./foxora stop
python3 -m tools.soroush_membership_probe --channel @mychannel
./foxora
```

## ⏳ پاک‌سازی خودکار پیام «اعلام مهلت گروه»

پیام تأیید مهلت (`تاریخ انقضای گروه تنظیم شد …`) با شناسه‌اش در رکورد همان
گروه ذخیره می‌شود و:

* با TTL برابر «زمان باقی‌مانده تا انقضا» به موتور `notice_cleanup` سپرده
  می‌شود (حتی اگر پروسه ری‌استارت شود، از فایل بازیابی می‌شود)؛
* در لحظهٔ انقضا صریحاً به صف حذف می‌رود (`EXPIRY NOTICE CLEARED`)؛
* با تعیین مهلت تازه، پیام مهلت قبلی همان لحظه پاک می‌شود.

بدون نیاز به هیچ دخالت مدیر. کلید رکورد انقضا نرمال‌شده (مثبت) است، اما
ارسال/حذف همیشه با شکل واقعی گروه (`-100…`) انجام می‌شود — قبلاً شکل مثبت
استفاده می‌شد که در سروش یعنی «کاربر خصوصی».

### کلمات ممنوعه: «کلمات بازنشسته»

`config/banned_words_retired.txt` واژه‌هایی را نگه می‌دارد که عمداً از لیست
حذف شده‌اند (مثل حرف تنهای «ک»)؛ این واژه‌ها هم از لیست مخزن و هم از فایل
ران‌تایم (`~/.foxora2/config/banned_words.txt`) پاک می‌شوند و `SpamDetector`
هر ورودی «یک حرف تنها» را نادیده می‌گیرد.

## 🖇 تشخیص لینک در بیوگرافی کاربران

قابلیت جدید: کاربری که بیوگرافی‌اش لینک دارد (وب، دامنه، لینک دعوت
تلگرام/سروش، `@username` در بافت تبلیغ) با همان سیستم اخطار/حذف/سکوت یا
اخراج فعلی ربات مدیریت می‌شود.

سیاست پیش‌فرض: **بیوی هر کاربری که در گروه پیام می‌دهد، همان لحظهٔ اولین پیام
بررسی می‌شود** (و بعد تا ۶ ساعت کش می‌شود). اسکن کامل «همهٔ اعضا» پیش‌فرض
خاموش است و فقط با دستور `بررسی بیو` یا `BIO_LINK_AUTO_SCAN_MEMBERS=1` انجام می‌شود.

- دستورها: `فیلتر لینک بیو` ، `لغو فیلتر لینک بیو` ، `وضعیت لینک بیو` ،
  `بررسی بیو` ، `لیست لینک بیو` ، `پاک لیست لینک بیو` ،
  `فیلتر آیدی بیو` / `لغو فیلتر آیدی بیو`
- مستندات و محدودیت‌های واقعی API: [`docs/BIO_LINK_FILTER.md`](docs/BIO_LINK_FILTER.md)

## ⚖️ دادگاه روباه (بازی ۵ نفره)

بازی گروهی ۵ نفره با قاضی داخلی ربات (بدون هیچ هوش مصنوعی/سرویس بیرونی):
`دادگاه` → ثبت‌نام با `شرکت` → تخصیص تصادفی نقش‌ها (شاکی، متهم، شاهد شاکی،
شاهد متهم، وکیل) → انتخاب جرم → شکایت → دفاع → دو شهادت → دفاعیهٔ وکیل →
رأی بر پایهٔ شواهد → **۱۳ سکه برنز** (تبرئه) یا **۲۰ سکه برنز** (محکومیت) +
مجازات ۶۰ ثانیه‌ای حذف پیام متهم.

* بازی برای **همهٔ اعضای گروه** است: `شرکت` در فهرست دستورهای بازی
  (`group_dispatch`) و پاسخ بازیکنانِ بازیِ در جریان از فیلتر هرزنگاری مستثناست.
* ثبت‌نام پیوسته است و بعد از ری‌استارت هم از همان فهرست ادامه پیدا می‌کند.
* قاضی **داخلی و آفلاین** است: ربات خودش شکایت، دفاع، دو شهادت و دفاعیهٔ
  وکیل را تحلیل می‌کند (مدرک، هم‌خوانی شهادت، اعتراف متهم، آلبای، شدت جرم و
  اصل برائت) — هیچ کلید API و هیچ تماس شبکه‌ای وجود ندارد.
* هر پرونده همیشه با رأی + سه دلیل فارسی + جایزه بسته می‌شود.
* ربات در مراحل پیام‌گیری هیچ یادآوری «نوبت فلانی است» نمی‌فرستد؛
  بی‌صدا منتظر پیام بازیکنِ نوبت‌دار می‌ماند.
* اجرای حکم (۶۰ ثانیه حذف پیام متهم) **بدون هیچ تبعیضی** است: مالک،
  ادمین ثبت‌شده، ادمین واقعی و VIP هم مثل بقیه حذف می‌شوند.
* همهٔ پیام‌های دادگاه **Bold** و ردیفی‌اند؛ هیچ نقل‌قولی استفاده نمی‌شود.

مستند کامل: [`docs/COURT_GAME.md`](docs/COURT_GAME.md)

```bash
python3 tests/test_court_game.py            # ۱۹۰ بررسی
python3 tests/test_court_join_all_users.py  # ۲۲ بررسی
```

## 📊 نمودار (رشد و ریزش اعضا)

دستور `نمودار` (بدون پارامتر) گزارشِ رشد/ریزش گروه را از **دفترِ عضویتِ
خودِ ربات** می‌سازد.

* **دسترسی:** فقط مالک سراسری (`config/owner.json`)، مالکِ ثبت‌شدهٔ گروه
  (`group_storage`) و ادمین‌های ثبت‌شده (`admin_storage`). فهرست از
  دیتابیس خوانده می‌شود، نه از متنِ پیام؛ کاربرِ دیگر پیامِ
  «فقط ادمین های ثبت شده مجاز هستند» می‌گیرد.
* **داده از کجا می‌آید؟** هر ورود/خروج (`ChatAction`) در جدولِ
  `membership_events` همان SQLite پروژه ثبت می‌شود
  (`modules/group_growth_events.py`). بارِ اولِ اجرای دستور، یک
  اسنپ‌شات از اعضای فعلی (`membership_baseline`) گرفته می‌شود تا اعضای
  قدیمی «ورودِ امروز» حساب نشوند؛ همان اسنپ‌شات شکافِ زمانِ خاموشیِ ربات
  را هم جبران می‌کند.
* **قانون دادهٔ ناقص:** اگر بازه‌ای به‌طور کامل پوشش داده نشده باشد
  (مثلاً ربات ۸ روز پیش نصب شده و بازه ۳۰ روز است) داخل همان براکت
  «تکمیل نشده» نوشته می‌شود — هیچ عددِ تخمینی یا جعلی تولید نمی‌شود.
* **بازه‌ها غلتان‌اند (نه تقویمی):** «امروز» = ۲۴ ساعتِ گذشته، «این هفته»
  = ۷ روزِ گذشته، «این ماه» = ۳۰ روزِ گذشته. هر ورود/خروجی که در آن
  پنجره ثبت شده باشد شمرده می‌شود؛ مثلاً اگر ۱۰ نفر در یک دقیقهٔ همان
  ۲۴ ساعت عضو شوند، هر ۱۰ نفر جداگانه ثبت و شمرده می‌شوند (هیچ رخدادی
  به‌خاطرِ نزدیکیِ زمانی ادغام یا حذف نمی‌شود).
* **نتیجه‌گیری:** مقایسهٔ مجموعِ عضو شده‌ها با مجموعِ ریزش‌ها در
  بازه‌های موجود → «گروه در حال پیشرفت هست» / «گروه در حال افت هست» /
  «داده کافی برای نتیجه‌گیری وجود ندارد».
* **تعداد اعضای فعلی همیشه واقعی است:** اول از دفترِ رخداد؛ اگر
  فهرست اعضا در دسترس نباشد (گروهِ بزرگ یا خطای شبکه) از عددِ
  اعلامیِ خودِ سروش (`participants_count`). اگر هیچ‌کدام نبود
  «تکمیل نشده» — هرگز صفرِ جعلی.
* **قالب‌بندی:** اعداد با ارقامِ بولدِ ریاضی (𝟬..𝟵) داخل براکت‌ها،
  عنوان‌ها و کلِ خطِ نتیجه‌گیری Bold، و همهٔ سلول‌های عددی داخل
  Blockquote سروش پلاس — با entity واقعی، نه Markdown خام.
* **راهنما:** در «لیست ادمینی» درست زیرِ «آمار گروه» آمده است:
  «📊 برای دیدن نمودار رشد گروه یا ریزش گروه دستور / « نمودار » /
  را ارسال کنید.» (کلِ متن Bold و خودِ دستور داخلِ نقل‌قول).

```bash
python3 tests/test_growth_chart.py   # ۱۲۶ بررسی
```

## 🎭 تیکه کلام

دستور `تیکه کلام` یک جملهٔ طنز/کنایه از فهرست می‌فرستد. متن با **Bold**
واقعی سروش (entity) ارسال می‌شود، نه Markdown خام.

* **بدون تکرار برای یک کاربر — حتی با ری‌استارت:** برای هر (گروه، کاربر)
  فهرست همهٔ جمله‌هایی که تا حالا گرفته روی دیسک نگه داشته می‌شود. تا وقتی
  حتی یک جمله از فهرست برای او باقی مانده، همان را می‌گیرد؛ ری‌استارت ربات،

* **بدون تکرار هم‌زمان بین کاربران:** جمله‌ای که در ۱۵ دقیقهٔ گذشته به کسی

## 🚦 پایداری و کندی (راند ۱۱)

پنج نقطهٔ کند/خطادار که در لاگِ کلاینت دیده شد، بدونِ دست‌زدن به مسیرهای سالم:

* **پاک‌سازی خودکار:** هرگز با شناسهٔ خام به `iter_messages` نمی‌رود (علتِ
  `IndexError: list index out of range`)؛ اگر peer پیدا نشود پاک‌سازی با پیامِ
  شفاف لغو می‌شود، نه با traceback.
* **کاربرِ حذف‌شده:** یک `GetUsersRequest … 404 NOT_FOUND` دیگر کلِ batch را
  نمی‌کشد؛ اول batch، در صورتِ شکست تک‌به‌تک (`modules/safe_rpc.py`).
* **`GetParticipants`:** کشِ ۶۰ ثانیه + single-flight + حداقل ۲ ثانیه فاصله
  (`modules/participant_cache.py`) — از ~۱۰ فراخوانی در ۱۴ ثانیه به حداکثر
  ۱ در دقیقه برای هر گروه.
* **Governor:** پیش‌فرضِ runtime و `.env.example` اکنون `auto` است؛ سقفِ delete
  فقط وقتی `BOT_RPC_TOTAL_LIMIT=3` باشد به ۲ می‌رسد و بعد از FloodWait برای
  ۶۰ ثانیه به ۱ برمی‌گردد. در Foxora2 با total پیش‌فرض ۲، سقف delete همچنان ۱
  است. اگر `.env` فعال خودش `BOT_RPC_DELETE_LIMIT=1` داشته باشد، همان مقدار
  صریح حفظ می‌شود.
* **حذف خودکار:** پنجرهٔ merge پیش‌فرض از ۶۰ms به ۲۰ms کم شده؛ burstها همچنان
  در تست به یک RPC batch شدند.
* **ترموکس:** نگهبانِ حافظه (`modules/memory_guard.py`) هر دقیقه RSS را
  می‌خواند و کش‌ها را هرس می‌کند (soft ۲۲۰MB / hard ۳۲۰MB).

جزئیات، مقایسهٔ گزینه‌های Governor و سناریوی تست هر تغییر:
[`docs/RPC_TUNING.md`](docs/RPC_TUNING.md)

```bash
PYTHONPATH=. python3 tests/test_slow_and_error_fixes.py   # ۳۵ بررسی
```

## 🧊 راند ۱۲ — کشِ `GetParticipants` و جداسازیِ لِین‌های Governor

* **ریشهٔ طوفان:** بررسیِ عضویت روی سروش `getParticipant` ندارد، پس
  `find_member` فهرست را صفحه‌به‌صفحه می‌خواند (۱۳۰۰ عضو ⇒ ۱۳ RPC). حالا هر
  صفحه از کشِ مشترک می‌آید: **TTL ۸ ثانیه**، حداقل فاصلهٔ ۱٫۵ ثانیه بین دو
  RPC واقعی برای همان گروه، و coalescingِ درخواست‌های هم‌زمان.
  لاگ: `GetParticipants cache hit chat=X` / `GetParticipants coalesced chat=X`.
* **Governor:** `GetParticipantsRequest` لِینِ مستقلِ `poll` گرفت
  (`BOT_RPC_POLL_LIMIT=1`)، خواندنِ سنگین دیگر سهمِ `notice`/`delete` را
  نمی‌خورد و heavy/poll وقتی صفِ send/notice دارد شروع نمی‌شود. لاگِ
  `GOVERNOR HOLD SLOW` حالا `culprit=` هم دارد.
* **پروفایل:** `GetFullUserRequest` یک کشِ کاربریِ ۴۵ ثانیه‌ای دارد
  (`GETFULLUSER cache hit user=X`) — یک کاربر در چند گروه یک RPC.
* **`PERF WARNING`:** حالا `slowest=…` و `notes=bio_check=…,banned_word=…`
  را هم می‌نویسد، پس گلوگاهِ هر پیامِ کند معلوم است.

جزئیات و جدولِ مقایسهٔ گزینه‌های Governor: [`docs/RPC_TUNING.md`](docs/RPC_TUNING.md)

```bash
PYTHONPATH=. python3 tests/test_heavy_poll_and_profile_cache.py   # ۳۵ بررسی
```
